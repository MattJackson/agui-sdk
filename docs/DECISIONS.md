# Design decisions (binding; they override API.md where the two conflict)

D1. **HTTP client stack.** Use hyper 1 + hyper-util + http-body-util (HTTP/1 only) with tokio `time`, and hyper-rustls 0.27 on rustls 0.23 (ring provider, webpki-roots).
- Do not use reqwest: it pulls 93 dependencies against this stack's 47 (`cargo tree` at the time of the decision).
- Remove the `reqwest-client` feature.
- `native-tls` goes through hyper-tls. It is the documented exception: an advisory-clean build needs Rust 1.80.

D2. **axum.** The `axum` feature depends on `axum-core` 0.5 + `http` 1, not the `axum` crate: 23 vs 41 dependencies. It provides IntoResponse/FromRequest integration usable from any axum 0.8 app.

D3. **PROC-17 / A2: the spec wins.** An unknown closed-set enum value is stripped with a warning. In a required position its container is dropped. It is never fatal. The upstream fixture `unknown-enum-value-role-fatal` asserts TypeScript's admitted gap, so the Rust lane keeps a local override with `intentional` text.

D4. **PB-12 typed-path byte parity.** An opt-in feature `preserve-order` enables `serde_json/preserve_order`, so typed events keep JS insertion order and the server encoder reproduces the 98-file corpus byte for byte. Without the feature, parity holds on the JSON-text path, and the gap is documented.

D5. **Clean room.** The implementation is written fresh from the spec. Nothing is copied from upstream pull requests #3214/#2778, the original upstream SDK or the TypeScript sources. Only files that are original work of the maintainer (not derived from those sources) are carried over, and independently written components (SSE, JSON patch, protobuf) are integrated as they are.

D6. **Spec data** is fetched at test time into `.spec-cache/`, pinned by `spec.lock`. It is never committed.

D7. **No AI attribution in commits, ever.** Use conventional commits, authored by the configured user.

D8. **A known role where `TextMessageRole` excludes it is malformed (audit 1, F9).** `TEXT_MESSAGE_START.role` and `TEXT_MESSAGE_CHUNK.role` of `tool`, `reasoning` or `activity` is fatal (`processing.invalid_value`, `expected one of ...`); a value outside every `Role` member (`narrator`) is still stripped with a warning, as D3 requires.
- Tie-break, spec text first: the schema says `TextMessageRole` "excludes tool, which is carried by TOOL_CALL_RESULT rather than streamed as text", and `processing.mdx` makes "a field the protocol DOES describe, carrying a value the schema rejects" fatal. A protocol role is 1.0 vocabulary, not material from a newer version, so it is a malformed known value rather than an unrecognised member.
- The corpus has no fixture for this case. Its closest one, `reasoning-message-wrong-role-fatal`, gives exactly this rationale for the pinned role ("any other value is a malformed known value rather than an unrecognised member"). The TS and .NET models reject any value outside the enum, so the stricter reading agrees.
- Enforcement models it as a set restricted from a wider domain (`Shape::Restricted`), the multi-valued analogue of the pinned role literal.

D9. **Optional `null`: exactly the registry, once per field per run, on every path (audit 1, F1, F3, F5).**
- Enforcement reads a whole `null` as absent only in the positions the deprecation registry lists (`compat::absent`, keyed by schema definition; `subagentRunId` on events only). Any other optional `null` (event or message `metadata`, `TEXT_MESSAGE_START.role`, ...) is a type mismatch, so fatal. This applies on the event path, to a host running `Enforcer` alone, and to the server's input admission. Spec: `metadata.mdx` ("MUST NOT be `null`"), `index.mdx` ("handled by a compatibility shim rather than by this rule"), and `DEPRECATIONS.md` ("every optional null not listed above" stays invalid).
- `RunAgentInput.state: null` is on the list. The registry has no row for it but says "the existing `RunAgentInput.state: null` parser tolerance continues", so tolerance shipped before this crate wins over the stricter reading.
- `DEPRECATIONS.md` says the conversions warn "once per field per run". The no-middleware fast path therefore sends the boundary every frame that has a member `null`, a plain or `\u`-escaped retired spelling, or legacy binary content, and it tells the boundary about every `RUN_STARTED`. The boundary's notices and the names it mints then follow the runs on every path and transport, as `processing.mdx` requires ("MUST reach the same verdict on the same event however it arrived").

D10. **A stream that carries runs after the requested one (audit 1, F2, F4).**
- `RunReport` describes the stream's last run (`run_id`, `status`, LIFE-45) and adds the requested run's own ending (`requested_run_id`, `requested_status`). A requested run that ended in `RUN_ERROR` is therefore never reported as successful because a later run on the same stream succeeded (`lifecycle.mdx`: "MUST NOT report the run as having succeeded"). The fixture `run-error-then-new-run-continues` still completes, because the stream is not a client failure.
- `Thread::absorb` matches the outcome by `requested_run_id`. It clears the in-flight mark on every path, so a refused outcome cannot leave the thread refusing every later run.
- Open interrupts stay open until a run that carried their resume entries closes with `RUN_FINISHED`. A resuming run that fails or is cut off leaves them open, and a later run on the stream that ends interrupted replaces them. This keeps `interrupt-resume.mdx` ("the most recent interrupted run on the thread"; "MUST NOT silently continue past an interrupt") at the thread level, where the reducer's per-run reset cannot.

D11. **`client` does not imply a TLS backend.** HTTPS is opt-in through `rustls` (recommended; implies `client`) or `native-tls`. Reasons: features are additive, so a default backend under `client` could never be removed by a `native-tls` user, who would build and ship rustls and ring as well; plain-`http://` deployments (in-cluster sidecars, loopback agents, tests) would compile a TLS stack they never use; and the MSRV and advisory story differs per backend (D1). The cost is a footgun, an `https://` URL with `client` alone, so every install line and quick start in the docs uses `features = ["rustls"]`, and `build()` refuses such a URL up front with `config.invalid` naming both features instead of failing on first use.

D12. **How the runner closes an invocation the agent left open (audit 1, server-4).** `lifecycle.mdx` requires a producer to close every open subagent before the `RUN_FINISHED` that ends a run, and `SubagentFinishedOutcome` has only `success` and `suspended`, with an absent outcome meaning success. Reporting a cut-off invocation as success would be wrong, so the runner's synthesized closers follow the run's closing:
- **Cancelled:** each still-active invocation, innermost first, gets `SUBAGENT_ERROR` with message `cancelled with the run` (no `code`).
- **Interrupt:** each still-active invocation gets `SUBAGENT_FINISHED` with outcome `suspended`. Its `interruptIds` are the run-level interrupts tagged with that invocation's `subagentRunId`; an invocation that raised none (suspended because a descendant interrupted, or the parent did) carries no `interruptIds` (the schema allows it to be absent).
- **Success:** unchanged. An agent that returned success with an invocation still open gets `SUBAGENT_FINISHED` with no outcome.
- `SubagentScope::fail` closes its still-active descendants with `SUBAGENT_ERROR` (`a parent invocation failed before this one finished`).
- `SubagentScope::finish` with a `suspended` outcome finishes its still-active descendants as `suspended` with no `interruptIds` (suspended because the parent was), as the runner's Interrupt closing does for an invocation that raised none. Any other outcome finishes them with no outcome. A `RUN_ERROR` closes nothing, as `subagents.mdx` says.

D13. **A tool call an approval interrupt names is answered by the resume entry (audit final, spec F1).** `Thread` keeps every call an interrupted run left unanswered in `pending_tool_calls()`; on an interrupted run the pending calls are derived the same way (`tool-calls.mdx`). A call whose id is the `toolCallId` of an open interrupt covered by the request's `resume` list is exempt from the TOOL-33 gate: its resume entry, `resolved` or `cancelled`, is its answer, and no tool message is required. This follows `interrupt-resume.mdx`, whose Message Flow resumes a `transfer_funds` approval with only `resume: [{interruptId, payload}]`, and whose producer rules treat "an approval-gated tool call with neither a result nor an entry answering it" as the uncovered case. Every other pending call, advertised or not, still needs a tool message. Restricting the gate to advertised tools was rejected: a call to an unadvertised tool "is not by itself a protocol violation — what to do with it is the consumer's decision", and `approve`/`is_advertised` already give such calls new-tool scrutiny (TOOL-42); exempting them would send dangling calls in ordinary success-outcome runs. The resume answer is not recorded in the message history, so `Thread::with_history`, which derives pending calls from history alone, lists such a call as pending again after the resuming run and the application must decline it before continuing; `Thread::restore` from a `ThreadSnapshot` keeps the exact pending set and needs nothing. Recording resume answers in persisted history would be new functionality and was not done.

D14. **Client memory bound (audit final, security S1, S2).** Default limits keep what one stream makes a client hold (state, history and activity content) near 252 MiB, and the figure is stated where the limits are documented.
- History growth (`max_history_bytes`) is charged in estimated resident bytes (`json::resident_bytes`), never serialized bytes: a `Value` slot per array element (capacity slack modelled below 128 elements), map storage (B-tree leaves of 11 entries at their minimum fill of five plus a separator, which a peer reaches by choosing member order, and the internal nodes above them, or the `IndexMap` layout, picked from the compiled types since any crate can switch on `serde_json/preserve_order`), string and key heaps rounded up to 16 bytes, `size_of::<Message>()` plus 110 bytes per held message and per call (slot, index entries, id copies; the verifier's and the run's tracking of it are charged by the bookkeeping ledgers, D25), and each content part's slot. Text, argument and encrypted-value deltas stay at their length. Patches charge each value they write plus the growth of the container it lands in (the container's storage at one more entry, and a new member's key); a patch's paths are not charged, as they are not held. Credits for what a patch frees use the same model: the values it overwrites or removes, and the slot each `remove` and `move` source vacates (the container's storage at one fewer entry, and the member's key), measured by the patch engine as it happens. A slot credit is dropped where the patch also credits the whole container (or an ancestor) it sits in, so a credit is never more than the content it frees was charged: no cycle drains the charge for content still held, and an add/remove, rename or rolling-log cycle nets zero instead of drifting the charge up, whether each operation is its own patch or one patch writes and frees a member of an object the content already held (such a value is credited from what the patch charged for it). A value one patch writes inside an array, inside an object the same patch created, or by `copy`, and then frees again, is charged and not credited (conservative). Measuring a credit walks the overwritten or removed values within a bank of 64 KiB of serialization work refilled at 8x each patch's wire size (`CREDIT_BANK`); a value whose walk exceeds that bank (for example a string member over about 64 KB replaced on every update) is charged and not credited, so the zero-drift cycles above hold only below that size. The walk of the value a patch writes is not taken from that bank.
- `tests/history_resident.rs` holds the estimate to 0.9x–1.4x of allocator bytes for maps (in sorted member order and in an order that leaves the B-tree at its minimum fill), single-member chains, messages, calls, content parts and the pipeline's id bookkeeping (open steps, reasoning spans, finished subagents, messages and calls a snapshot dropped; D25), and to 0.7x for large parsed arrays (their untouched capacity tail is not resident) and 0.75x for an `IndexMap` grown member by member (its entry vector doubles). Streamed text is charged at its length; the `String`'s capacity slack beyond that is not resident for large strings.
- Defaults: `max_history_bytes` 128 MiB; `PatchLimits::max_nodes` 180,000 (growth floor `min_nodes` stays 1,000,000, above the ceiling, so under defaults only the ceiling refuses growth); `Limits::max_container_entries` 150,000, below the node ceiling so a structure-only snapshot at the entry limit still takes growing deltas. A text-heavy snapshot within the entry limit can sit above the ceiling (node units count text at one per 64 bytes); any delta that grows it then ends the stream.
- The per-patch walk budget follows the growth allowance before the ceiling clamps it (`caps()`), so the lower ceiling bounds memory and not CPU: every patch keeps the 4,000,000-unit walk budget it had.
- A node unit or container entry costs 32 B (scalar array element) to about 690 B requested, about 720 B with allocator size classes (a single-member object with a key of up to 63 bytes, which costs no extra unit: a whole B-tree leaf plus the key's block; about 420 B with `preserve-order`). Worst case per stream, 64-bit: about 124 MiB of state and patched activity content (180,000 units of the worst shape; `tests/history_resident.rs` checks the bytes requested stay under it), plus 128 MiB of history and id bookkeeping growth as estimated (D25): about 252 MiB.
- Not included: the event being parsed (at most 150,000 entries, about 103 MiB in the worst shape, plus its text; a chunk that opens an item holds its metadata twice while it is expanded, so up to about twice that), the one event that crosses the history limit, and history restored with `Processor::with_history` or kept by a `Thread` across runs, which is the host's to trim.
- The entry limit also bounds server input admission, `validate_*`, the client transport and the protobuf decode budget: a hostile client is bounded by the same figure. 150,000 entries still admits a run input or `MESSAGES_SNAPSHOT` of tens of thousands of messages.

D15. **Per-feature CI lanes build the library alone (audit final, api L1).** `crates/test-support` enables `client`, `server` and `proto` on `agui-sdk`, and Cargo unifies that into every build that compiles dev-dependencies or selects the workspace, so a test lane cannot show what one feature alone compiles. Each `msrv-features` row (one per Cargo.toml feature, plus one with no features) therefore checks the library alone on the feature's floor toolchain (`cargo rustc -p agui-sdk --lib --no-default-features --features <f> --profile check -- -D warnings`) and lints it on latest stable (`cargo clippy -p agui-sdk --lib --no-default-features --features <f> -- -D warnings`). `cargo rustc` is used rather than `RUSTFLAGS="-D warnings" cargo check` so the flag reaches `agui-sdk` only and no dependency is rebuilt. The `msrv` job checks the no-feature library the same way on Linux, macOS and Windows; `docs` builds rustdoc for the library alone with no features and each feature, the list read from Cargo.toml; `lint` fails if a feature has no `msrv-features` row. Test steps keep the harness's features and say so in their names. D18 records the async audit's side of the same fix (lane names and OS claims, and the configurations no test lane covers).

D16. **Release publishing never compiles with a credential present (audit async, M2).** A verifying `cargo publish` or `cargo package` runs every dependency build script and proc-macro with the step's environment, so it would see `CARGO_REGISTRY_TOKEN`; and the publish job's job-wide `id-token: write` lets any of its steps mint an OIDC request token. So the verify build runs in qa.yml's `package` job (`cargo publish --dry-run --workspace --locked`), which holds no secret and no `id-token` and gates the release (`publish` needs `verify`, the qa run on the tag). release.yml's `publish` job runs only `--no-verify` cargo commands, with the registry token in the two publish steps' env only. qa.yml's `lint` job fails if any piece of a non-comment, non-`name:` release.yml line (split at `&&`, `;`, `|`, `(` and backticks) contains the word `cargo` and is not `cargo [+tc|-flag ...] publish|package ... --no-verify` on one line; `--dry-run` alone does not pass, because it still builds. Lines it cannot read that way fail closed. It does not see cargo run indirectly (a script file, `$CARGO`, an action). Every action in the job (checkout, rust-toolchain, crates-io-auth, attest, cosign-installer, cosign) runs with `id-token: write`; they are pinned, and the auth, attest and signing ones need it.

D17. **A custom transport is contained like every other extension (audit async, M3).** A panic while a transport opens or is read fails the run with `transport.stream_read` ("the transport panicked"), with or without middleware; observers see one `on_finish` with that error, and nothing unwinds into the caller. The code is the existing `StreamRead` (kind Transport, never retryable), not a new one; `Internal` would blame this crate for user code. Residuals: a panic in a transport's destructor is not contained, and a bug panic inside the built-in HTTP transport also reads as `transport.stream_read` (the panic hook still prints it). On the server, an agent's future and context are dropped under `catch_unwind` both when the run is decided and when the stream is dropped mid-run (a disconnect), whatever `catch_unwind` is set to.

D18. **What a feature lane covers (audit async, M1, L3; with D15).** The test harness (agui-test-support) enables `client`, `server` and `proto`, and Cargo unifies dev-dependency features into every build that has test targets (`--all-targets`, `--lib` tests, `--tests`). Per-feature claims are therefore made only for library-alone builds (the lanes are D15's), which pull in no dev-dependency: qa's `msrv-features` runs, for no features and for each feature by itself, `cargo rustc -p agui-sdk --lib --profile check --no-default-features [--features <f>] -- -D warnings` at the feature's floor and `cargo +stable clippy -p agui-sdk --lib --no-default-features [--features <f>] -- -D warnings`; dev.yml clippies the library alone with no features. Test lanes are described as "<f> plus client, server, proto", the workspace clippy runs as effectively client+server+proto, and docs name each lane's OS (`msrv` on Linux, macOS and Windows; the feature lanes on Linux). Tests of a no-proto or server-less configuration do not run; closing that needs a test crate that does not depend on the harness.

D19. **native-tls offers TLS 1.2 at least (audit final, security S6).** `native_connector` sets `min_protocol_version(Tlsv12)`, matching the rustls backend's `with_safe_default_protocol_versions` (TLS 1.2 and 1.3), whatever the platform would otherwise allow (native-tls defaults to TLS 1.0). Recent macOS and Windows and OpenSSL 3 at its default security level already refuse legacy TLS; the floor makes the guarantee the crate's rather than the platform's. `tests/native_tls_floor.rs` (Linux, all-features lanes) forces a permissive OpenSSL configuration and checks the ClientHello offers nothing below 1.2.

D20. **The axum extractor reads at most min(axum `DefaultBodyLimit`, 16 MiB) (audit final, security S3).** `AguiRequest::from_request` refuses a `Content-Length` over 16 MiB with `413` before reading, and reads the body through `http_body_util::Limited` at 16 MiB, so `DefaultBodyLimit::disable()` lifts only axum's cap. `InputPolicy::max_body_bytes` still applies after the read and binds when lower. The extractor cannot see the `ServeConfig` (its state is generic, and a `FromRef` bound would break stateless handlers), so the read cap is the crate's default; an application that accepts larger run inputs reads the body with its own limit and builds `AguiRequest::new`.

D21. **Per-stream diagnostic volume is not capped (audit final, security S5).** Diagnostics are emitted as events are processed, and each one is bounded twice: per event (`Limits::max_diagnostics_per_event`) and in the client's run report (`max_report_diagnostics`). Their total volume over a stream is therefore linear in the input, which the per-frame and total limits (`max_frame_bytes`, `max_container_entries`, `max_history_bytes`, the patch node ceiling) already bound. A per-stream cap on what the sink receives is deliberately not imposed: the sink would go quiet once it was reached, hiding every later problem on the stream, and a host that wants rate limiting or sampling does it in its own `DiagnosticSink`.

D22. **Release notes describe the release (audit final, round 2).** A version's CHANGELOG section states what that version ships, relative to the previous published release; for 0.9.0, the first release, it states the shipped values only, with no "was X" for values no release had. Maintainer instructions live in CONTRIBUTING ("Cutting a release"), not in a section that becomes a GitHub Release body. `release.yml` refuses a tag whose `## [X.Y.Z]` heading is not dated `YYYY-MM-DD`; qa does not check it, because `dev` legitimately carries `TBD` until release day.

D23. **Undefined operation members are preserved, `from` included (audit final, round 2; owner decision).** RFC 6902 defines `from` only for `move` and `copy`; on every other op it is an undefined member, which `processing.mdx` says MUST be preserved and the schema leaves open. `PatchOperation` reads `from` untyped and decides once `op` is known. On `move`/`copy` a string is the source pointer, `null` reads as absent (apply reports it missing) and any other type is malformed and fatal (SNAP-09). On any other op a string `from` stays in `PatchOperation::from`, as `value` on a `remove` stays in `value` (PROC-15), and a `from` of any other type, `null` included, goes to `extensions`; either way the event is delivered whole on the JSON path. The protobuf encoder carries a string `from` as field 3 on any op and drops a non-string one on an op other than `move`/`copy`, as it drops every extension member (PB-16); a non-string `from` on `move`/`copy` stays an encode error.

D24. **An SSE event whose `data` is empty is dispatched and fails as a non-event frame (audit final, round 2; owner decision).** WHATWG's "process the field" step appends the value plus LF, so after one empty `data` field the buffer is `"\n"`, not empty, and dispatch fires an event with data `""`; `processing.mdx` makes a frame whose bytes map to no event a decode failure that every transport answers the same way, and the TypeScript reference fails it too (`JSON.parse("")`). `SseDecoder` therefore dispatches it and the pipeline refuses it with the same code as `data:\ndata:\n\n`. This reverses e4d208d, which misread the dispatch step and dropped the event, leaving `data: ` skipped while `data:  ` and two empty lines were fatal. Keep-alives are comment lines (SSE-08) and are still ignored.

D25. **Id bookkeeping is charged to the history budget (audit final, round 2).** Everything the client pipeline keeps under a peer-chosen key is charged to `Limits::max_history_bytes` for as long as it is held, so a stream of open steps, reasoning spans, subagent invocations, or messages that a `MESSAGES_SNAPSHOT` drops right after they open, can no longer make a default-limits client hold unbounded memory, and D14's 252 MiB stays true.
- What is charged: the consumer verifier's step names and their owners, reasoning spans, subagent sets, text, tool-call and reasoning item tables (with a subagent-owned item's chunk lane share), activity owners and the stream-wide message-id set; the reducer's run tool-call tables (`started`, `ended`, `answered`) and the copies `finish_run` makes of the run's pending calls.
- How: each entry is estimated in resident bytes (a hash-table entry at twice its size for the table's load, plus the id's own `Arc` heap rounded to 16 bytes), charged when inserted and credited from the same figure when removed or its table cleared, so a credit never exceeds its charge. The verifier keeps the running sums; `Processor` hands their total to the reducer (`set_bookkeeping`) after each event is verified and before it is applied, which adds the change to the history growth; the reducer's existing check ends the stream with `processing.limit`. No new limit, knob or error code.
- The stream-wide message-id set is never credited (BASIC-15 keeps a dropped message's id reserved); ids given to `with_known_messages` (the history a processor starts from) are not charged, as growth counts from that history (D14). Retained step names (up to 64) stay charged across runs, because they stay resident.
- Within a stage an id has one `Arc`, charged once: the verifier's item and activity tables reuse `known_messages`' `Arc`, and `ended`/`answered` reuse `started_set`'s for a call the run started (any other id keeps the event's `Arc` and is charged its heap, so `pending_tool_calls()` is unchanged: a result recorded before its call is reopened still answers it). This also frees the second copy of a long id that `TOOL_CALL_END` used to keep. Across stages a shared id is charged once per stage, which over-states long ids (up to about 3x on the id bytes) and nothing else.
- `ITEM_OVERHEAD` no longer includes the verifier's and the run tables' share (280 became 110 bytes beyond a `Message` slot), so held messages are not charged twice; the existing bands still hold.
- Consequences: the pending-call copies are charged when `RUN_FINISHED` (or `RUN_ERROR`) makes them, so a run whose pending calls push the growth past the limit ends with `processing.limit` on its terminal event, and until the next `RUN_STARTED` they shrink the headroom later activity patches are measured against.
- Rejected: a per-id length cap (ids are opaque in the spec, and 2,000,000 short step names hold 800 MB without long ids); a `max_open_items` knob (new public surface, and it misses closed entries and the message-id set); pruning on snapshot drop (open items and the BASIC-15 set cannot be pruned, and pruning closed entries would change reopen ownership checks); a tombstone charge at message drop (misses steps, spans and subagents, and drifts on repeated drops).
- Residual: a `ConsumerVerifier` used without a `Processor` has no budget of its own; its host bounds the stream.
- A chunk lane holds no peer string of its own (audit final, round 3). Its item id and owner share the `Arc`s the verifier charges; the opener fields later chunks are compared against (`toolCallName`, a text `name`, and a tool call's `parentMessageId`) are kept as 64-bit fingerprints. The lane used to keep the opener's `parentMessageId` itself, which the history's own copy did not share and nothing charged, so one subagent lane per active subagent naming a long parent held memory in proportion to the wire. Fingerprints (the chunk lanes' and the producer verifier's tool-name and text-name checks) are SipHash under keys drawn at random once per process, not std's fixed `DefaultHasher::new()` keys, so a peer cannot compute two values that collide and a conflicting repeat is refused as the spec requires; an accidental collision is a 2^-64 event. Rejected: charging the copy to this budget (the lane needs no copy).

D26. **The rejection body in the error chain is escaped (audit final, round 2).** The source attached to `transport.http_status` displays the server's error body with control characters escaped (`char::escape_default`), like every other peer-chosen text in `Error`'s `Display`, so a server cannot forge log lines or terminal escapes through `{:#}` or a chain-walking logger. Compact JSON bodies read unchanged; a body with raw control characters (pretty-printed JSON's newlines) reads escaped and is no longer parseable as-is. A raw-body accessor would be new public API and was not added. Residual, as for `Error`'s `Display`: format characters that are not control characters (bidi overrides) pass through.

D27. **`MemoryInterruptStore` bounds the bytes of the thread ids it keeps (audit final, round 2).** Besides `max_threads`, the store evicts the least recently recorded threads while their ids would total more than 1 KiB per allowed thread (about 10 MiB with the defaults), so a client cannot pin multi-megabyte thread ids for the TTL. One id over the whole budget is still kept, alone. No knob was added: the budget scales with `max_threads`. Interrupt payloads are the agent's and are not counted. An evicted thread's resume entries read as unrecognised, as for any eviction. Rejected: refusing long thread ids (it would turn a working resume into a failure), and keying on a hash (the id is needed for comparison anyway).

D28. **The retired-thinking shim's span table is bounded and charged (audit final, round 3).** The compatibility boundary names the `THINKING_*` spans it translates, so a later unnamed `THINKING_END` can be given the latest open span's id. It kept a `String` copy per `THINKING_START` and dropped it only on `THINKING_END` or `RUN_STARTED`. A span opened with `THINKING_START X` and closed by a 1.0 `REASONING_END X` (which the verifier accepts, and which skips the boundary on `push_json`'s fast path) left the copy behind, so repeating the pair grew client memory without bound outside D25's budget. Now:
- the table holds one entry per open id, sharing one `Arc<str>` between its two indexes; a `THINKING_START` naming an id already open adds nothing (the verifier judges the duplicate open);
- a 1.0 `REASONING_END` naming a tracked span closes it in the shim too. `Processor::push_json` routes a frame containing `REASONING_END` through the boundary while the shim tracks any span (a byte scan, only then); the client's parsed-frame path and the middleware upstream run the boundary on every frame already;
- the table's estimated resident bytes (D25's model: two entries at twice their size plus the id's `Arc` heap, and the open message's id text) are charged with the verifier's bookkeeping. `Processor` adds its own boundary's figure, and the client driver hands the processor the figures of the boundary it runs for parsed frames and of the one in the middleware upstream (summed over live upstream stages, charged from the next frame the processor sees).
- The client's middleware-path boundary is charged to the processor with every frame that reaches it, and it also enforces `max_history_bytes` on its span table together with what the processor already charges, so a middleware that drops the translated frames cannot let the table grow unchecked (the run ends with `processing.limit`).
- Residual: a boundary a host runs in its own code before `push_value` is not charged. Its entries are open spans the verifier also charges, unless the host drops the translated frames before they reach the verifier.
- Rejected: dropping the shim's state on any 1.0 reasoning frame (an unnamed `THINKING_END` after a mixed span would lose its name), and a count cap on the table (ids are peer-chosen, so a count does not bound bytes).

D29. **A minted carrier gives its id up to the producer (audit final, round 3).** A parentless tool call joins a carrier the reducer mints under the call's id, as in the TypeScript reference. The producer never chose that id for a message, and `messageId` and `toolCallId` are separate identifiers, so a later conformant `TEXT_MESSAGE_START`, `REASONING_MESSAGE_START`, chunk, `TOOL_CALL_RESULT` or `ACTIVITY_SNAPSHOT` with the same id used to reopen the carrier: reasoning text became assistant content (with a `stream.conflicting_reopen` blaming the producer), and a result left two messages under one id. Now the reducer remembers the ids it minted carriers under (charged to the carrier, D25). When the producer opens a message under one, the carrier is renamed to a fresh `<id>~<n>` (itself minted) and the producer's message opens under the id. The carrier keeps its position, calls and owner; `run_message_ids` follows the rename, and pending calls derived after it name the new id. A carrier the producer names as a later call's `parentMessageId`, or that a `MESSAGES_SNAPSHOT` replaces, is the producer's from then on. Renames are per reducer: a carrier in the history a processor starts from reads as the producer's, as in the reference. Residual: an application that recorded the carrier's id from an earlier change notice now finds it naming the producer's message. Rejected: opening the producer's message under the same id without a rename (two messages under one id, and the index would have to leave the first occurrence), and minting carriers under a reducer-chosen id from the start (diverges from the reference, and the producer could still use that id).
