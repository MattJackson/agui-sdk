# SPEC-MAP: ledger rows → implementation → proving test

Every AG-UI 1.0 requirement-ledger row classified **sdk-ownable** (453) or
**sdk-assistable** (41) is mapped below to the item that implements it and to
the integration test that will prove it. Paths are relative to the
`agui_sdk` crate root (`server::Runner::run` is `agui_sdk::server::Runner::run`).
Application and informative rows (22) and the 20 draft-1.1 rows are out of
scope until 1.1 freezes, and are not listed.

Source of the rows: the requirement ledger (rev 2) and its compliance
classification. Row text is a paraphrase from the ledger, not spec prose.

## How this file is used

* **It is the gate's input.** `cargo xtask trace` (implemented by
  `agui-test-support::traceability::gate_with`) parses the table under "The map" (the summary table above it is not read). A row
  passes when at least one test function in the named file carries a
  `/// covers: <ID>` line. The function must be a test that runs: a tag on a
  function without a test attribute, or on an `#[ignore]`d test, covers
  nothing and fails the gate. Rows with two files (`a.rs + b.rs`) need a tagged
  test in each. A `covers:` tag naming an ID absent from this table also fails
  the gate. The table format is therefore fixed: one row per line, nine
  columns, ID first.
* **Implementation column.** The first item named is where the behaviour
  lives; items after a `;` are the other places that take part. `client:` /
  `server:` split the two halves of a `both` row.
* **Fixtures column.** Upstream stream-corpus fixtures that exercise the row.
  The corpus lane (`tests/corpus_streams.rs`) runs every fixture regardless.
  This column documents which rows the corpus also proves.
* **Flag column.** Non-empty only where the API cannot fully express the row.
  These rows are summarised next.

## Rows the API cannot fully express

| Row | Status | Why, and what the API does instead |
|---|---|---|
| PB-12, ARCH-06 | partial without `preserve-order` | Byte parity with the upstream protobuf corpus is reached through `proto::encode::encode_json`, which reads member order from JSON text, in every build. A server encoding *typed* events reproduces the corpus byte for byte too when the crate feature `preserve-order` is on (decision D4: it enables `serde_json/preserve_order`, so open objects keep insertion order; the encoder still writes integer-like keys first, as JavaScript does). Without the feature, typed open objects (`state`, `metadata`, `CUSTOM.value`) are encoded in sorted map order: conformant, since `http-protobuf.mdx` allows encoders to order open-object entries differently, but not byte-identical. The corpus lane runs the JSON-text path always and a typed-path variant with `preserve-order`. |
| PROC-17 | resolved (D3) | Spec wins: an unknown value of a closed string set is stripped with a warning and never fatal; in a required position its container is dropped (`Message.role` drops the message, `ReasoningMessageStart.role` the event, a `PartSource` arm the part). The upstream fixture `unknown-enum-value-role-fatal` asserts the TypeScript reference's admitted gap, so the Rust lane overrides it as `intentional` in `tests/corpus/rust-lane-overrides.toml`. |
| TOOL-27 | partial | Deciding that nothing remains is agent behaviour; the SDK documents it on `server::Agent` and `RunOutcome::success`. What the SDK owns is tested behaviourally: once the agent returns `RunOutcome::success()`, `Runner::run` closes the run without waiting for any frontend result, with the unanswered calls in `pendingToolCallIds`. |
| CAP-03 | partial | `server::http::capabilities_response` (and `server::axum::AguiResponse::capabilities`) overwrite `transport.streaming` and `transport.httpBinary` with what the endpoint actually serves (`ServeConfig::protobuf` and the `proto` feature); the author cannot declare them. The rest of a declaration is the author's claim and cannot be checked. |
| REAS-25 | partial | `client::Thread` returns encrypted values only through the `AgentClient` that received them. A history the application copies to another agent by hand is outside the SDK's reach; rustdoc on `RunReport::messages` says so. |
| TRN-14 | docs only | A SHOULD to *document* a custom transport. It is met by rustdoc on `client::transport::Transport` and `server::http`; there is nothing to execute. Its test asserts that the rustdoc sections exist (doc-test of the trait docs). |

No other gated row is blocked by the API shape. Several rows are true by
construction rather than by a check: `event::Event` is closed, so a server
cannot emit an undescribed type (PROC-36), and `server::Agent` has no inbound
channel during a run (PAT-02). Their tests are compile-time or
construct-and-observe tests.
